# Git 提交规范

## 提交时机与范围

- 任务达到可独立审查、已完成相应验证的逻辑完成点时提交，不按编辑次数或文件数量拆分提交。
- 一个提交只包含同一逻辑目标的改动；未完成或未验证的内容保留在工作区，不提交半成品。
- 最近一次提交需要补充同目标的小修正，且尚未开始新的逻辑改动时，优先 amend；已共享的提交不自动改写。
- 提交前检查 `git status`、改动及新文件，只暂存本次完成点涉及的路径或代码块，排除用户原有和其他任务的改动。
- 核对 `git diff --cached` 与 `git diff --cached --check`，确认缓存、日志、构建产物及自动生成工程文件未进入提交。
- 只读审查不产生提交。推送、远端配置和历史改写按用户明确授权执行，不由本技能扩大范围。

## 提交信息

标题格式为 `<type>(<scope>): <中文摘要>`。

- type 采用准确的类型，如 feat、fix、refactor、perf、test、docs、build、ci、chore。
- scope 必填，使用稳定功能域，如 init、package、window、tree、api、skill；不机械使用文件名或类名。
- 摘要描述已经完成的结果，避免“更新代码”“优化逻辑”等模糊表述。

每次提交都填写以下正文，栏目顺序保持一致：

```text
<type>(<scope>): <中文摘要>

变更内容：
- <已经完成的行为或结构变化>

原因：
- <真实动机或问题来源>

验证：
- <实际执行的检查与结果；未运行时说明原因>
```

正文不按文件逐项复述 diff，也不把计划执行的检查写成已通过。

## 执行与完成

- 多行提交信息写入工作区外的临时文件，使用 `git commit --file`，避免命令行转义破坏中文与换行。
- 不修改全局 Git 身份或默认配置。初始化仓库时使用已确认的分支和现有身份。
- 提交后检查提交内容、信息和工作区状态，报告提交哈希及尚未提交的内容。
